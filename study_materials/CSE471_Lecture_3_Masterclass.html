Requirements Analysis

Requirements Determination

Diagnosing what a system actually needs, not just what users want.

Part 0

🧠 The Big Picture

Requirements gathering is like being a detective. You're not just asking people what they want — you're investigating what they NEED. Users often know their pain but not the cure. Your job is to diagnose, not just prescribe.

Why does this phase matter so much?

45% of all software errors originate in requirements. Getting requirements wrong is the most expensive mistake you can make.

The core transformation: The analysis phase transforms vague wishes into precise specifications — it's the bridge between 'we need something' and 'here's exactly what we're building.'
Part 1

📝 Requirements Specification

A requirement is a statement of what the system must do or what characteristics it needs to have. There are 5 primary types.

5 Types of RequirementsClick to reveal details
Business Requirements: What the business needs.
Example: "Increase market share by 10% in the next quarter."
User Requirements: What users need to do with the system.
Example: "A customer should be able to review their past orders."
Functional Requirements: What the software should do (processes and information).
Example: "The system must allow a user to search products by name."
Nonfunctional Requirements: Characteristics the system should have (quality attributes, constraints).
Example: "The system must return search results in under 2 seconds."
System Requirements: How the system should be built technically.
Example: "The application must be built using React and Node.js."
Part 2

⚖️ Functional vs Nonfunctional

This is the MOST IMPORTANT distinction in the lecture.

Functional

Process the system performs OR information it provides to support user tasks.

  • "System shall allow user to search products by name"
  • "System shall generate monthly sales report"
Nonfunctional

Quality attributes, constraints, interfaces.

  • "Search returns results in under 2 seconds"
  • "Compatible with any browser"
⚠️Don't confuse WHAT the system does (functional) with HOW WELL it does it (nonfunctional). 'Search for products' is functional. 'Search returns results in under 2 seconds' is nonfunctional.

Categories of Nonfunctional Requirements

Category Description Example
Operational Physical/technical environment "Runs on Android", "Compatible with any browser"
Performance Speed, capacity, reliability "Response < 2 seconds", "Supports 300 concurrent users"
Security Access restrictions, safeguards "Only managers see personnel records", "Virus protection"
Cultural/Political Legal, policy, cultural factors "Comply with Data Protection Act", "Buy only Dell"
Self-test: A client says 'The system must work on iPhones and Android devices.' Is this functional or nonfunctional?
Reveal Answer

Nonfunctional (Operational). It dictates the environment in which the system operates, not a specific user task.

Self-test: A client says 'Users should be able to reset their password via email.' Functional or nonfunctional?
Reveal Answer

Functional. It describes a specific task/process the system must perform.

Part 4

🗣️ Requirements Gathering Techniques

5 Core TechniquesClick to see when to use
Interviews: Direct Q&A with stakeholders.
When to use: Need in-depth, nuanced information from key individuals. Good for exploring complex issues.
JAD Sessions (Joint Application Design): Structured group workshops.
When to use: Resolving conflicts between departments, achieving consensus, cross-functional processes.
Questionnaires: Written surveys for large groups.
When to use: Gathering standard information from a widely distributed or large user base.
Document Analysis: Studying existing forms, reports, procedures.
When to use: Understanding the current ("as-is") system, finding out what data is actually collected.
Observation: Watching users perform current tasks.
When to use: Validating what users actually do vs what they say they do. Discovering workarounds.
Self-test: Your team wants to see how Amazon handles returns to improve your own return process. What technique?
Reveal Answer

Benchmarking (Informal observation). Experiencing someone else's system to gather ideas.

Part 5

🎯 Requirements Analysis Strategies

Strategy Business Value Cost Breadth Risk
Problem Analysis Low Low Narrow Low
Root Cause Analysis Medium Medium Narrow Low
Duration Analysis Medium Medium Medium Low
Activity-Based Costing Medium Medium Medium Medium
Benchmarking High High Wide Medium
Technology Analysis High High Wide High
Activity Elimination High Medium Wide High
Strategy DetailsClick to expand
Ask users for problems AND solutions. Quick but incremental. Rarely finds high-value improvements because users are trapped in their current mental model.
Calculate time per step vs total process time. Large gap = fragmented process. Fix with Process Integration (fewer people, broader roles) or Parallelization.
Activity-Based Costing: Calculate cost per step (direct + indirect). Focus improvement on most costly steps.
Study how OTHER organizations do the same process. Informal: experience their process as a customer.
Analysts + managers list interesting technologies. Identify how each could benefit the business.
"What if we just stopped doing this?" Force-fit test all activities. Most radical approach.
Self-test: You find that a 10-step process takes 3 hours per step but the total process takes 2 weeks. What analysis strategy identified this?
Reveal Answer

Duration Analysis. It specifically looks at individual step time versus the overall time to find fragmentation.

Self-test: A manager asks: 'What if we stopped generating the weekly inventory report entirely?' What strategy?
Reveal Answer

Activity Elimination. The most radical approach: questioning the necessity of a task outright.

Part 6

🔍 Deep Dive: Problem vs Root Cause

A critical distinction for analysis strategies.

Problem Analysis

Users identify problems AND propose solutions.

  • Incremental improvements.
  • Dangerous: users propose fixes within their current flawed mental model.
  • "Make this form load faster."
Root Cause Analysis

Users identify problems only. Analysts find root causes.

  • Deeper, systematic fixes.
  • Solves MULTIPLE problems at once by fixing a shared root cause.
  • "Eliminate the form entirely because the data is redundant."
Problem Analysis sounds efficient but it's dangerous — users will say "make the form faster" when the real fix is "eliminate the form entirely." Root Cause Analysis is slower but finds fixes that solve multiple symptoms at once.
Self-test: You want users to tell you their problems but NOT suggest solutions. Which strategy?
Reveal Answer

Root Cause Analysis.
